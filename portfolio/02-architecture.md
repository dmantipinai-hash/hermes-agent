# Архитектура агентской оболочки

> Обновлено 08.09.2026. Базис — форк открытого Hermes (линия v0.16),
> развивающийся независимо: своя линия релизов (v1.1), апстрим-обновления
> вливаются вручную и осознанно, автоматического обновления нет.

## Общий силуэт

Один агент-ядро, живущее одновременно в CLI, мессенджерах (Telegram и ~20
платформ через шлюз), TUI и desktop-приложении. Возможности наращиваются
краями — скиллами, плагинами и сервис-инструментами, — а не ростом ядра.
Над этим силуэтом проект достроил четыре подсистемы, которых нет в базовом
Hermes; они и есть предмет этого кейса.

```
                 ┌────────────────────────────────────────────┐
                 │  Человек (архитектор, заказчик, приёмка)   │
                 └──────┬───────────────────────────┬─────────┘
                        │ Telegram / CLI            │ постановки, ревью
                 ┌──────▼──────┐             ┌──────▼───────┐
                 │  Локи (прод)│◄── mailbox ──│ ZCode        │
                 │  main-профиль│   доставка  │ (разработка) │
                 └──────┬──────┘             └──────────────┘
        ┌───────────────┼────────────────────────────────┐
        │               Агентское ядро (форк)            │
        │  память v2 · оркестрация · осознанность ·      │
        │  экономика токенов · шлюз · cron · профили     │
        └───────────────────────────────────────────────┘
```

## Подсистема 1. Память v2 — «помнит выборы, не съедает промпт»

- **Типизированное хранилище**: SQLite (WAL + FTS5), одна база на профиль.
  Типы записей — fact / decision / constraint / pattern / preference;
  статусы — active / deprecated / pinned; провенанс — кто и когда записал.
- **Граф решений**: смена решения — это не перезапись, а новая ревизия со
  связью `supersedes`; история «что решили раньше и почему передумали»
  сохраняется. «Карта напряжений» подсвечивает конфликтующие активные
  решения прямо в выдаче поиска.
- **Два яруса видимости**: замороженный на время сессии снапшот промпта
  (lane-структура: ограничения → стоящие решения → контекст; бюджет в
  символах) и «холодный» весь остальной склад, находимый поиском.
  Per-ход надстройка — оркестратор памяти: по интенту запроса собирает
  контекст-пак только из релевантного, в пределах токен-бюджета.
- **Шина памяти**: единый API recall/remember с подписками потребителей
  («субагенту — брифинг только его проекта»), групповой откат записей
  сессии.
- Инвариант, ради которого всё: **большая память ≠ большой промпт**;
  кэш промпта не ломается; поиск — лексический (FTS5, стемминг, алиасы,
  ё→е-фолдинг), вектора — сознательно отложены.

## Подсистема 2. Оркестрация — «команда агентов на одной доске»

- **Роли делегирования**: специализированные профили (researcher, coder,
  reviewer, analyst, writer) с фиксированными наборами инструментов +
  capability-ось leaf/orchestrator (кто может плодить детей).
- **Канбан-доска** на SQLite как координационное ядро: диспетчер поднимает
  воркеров-профилей, заявки с защитой от зависаний.
- **Два режима обмена**: синхронный `ask_agent` (диалог с профилем) и
  асинхронный mailbox — **мягкая доставка сообщения работающему агенту**:
  сообщение дописывается в тред задачи и подхватывается моделью по ходу,
  без прерывания работы. Это же — мост между профилями.

## Подсистема 3. Осознанность — минимальный метакогнитивный контур

Детерминированный цикл DETECT → RECALL → RECORD без единого LLM-вызова:
застревания (повторные неудачи инструмента) детектируются счётчиками,
прошлый опыт поднимается из памяти и дописывается нотой в результат
инструмента, честные исходы записываются в память как паттерны.
Развитие — реестр методов мышления (ТРИЗ/АРИЗ и др.) — в проектировании
(см. планы).

## Подсистема 4. Экономика токенов

Телеметрия с нулевым следом в контексте модели: сессионный и по-модельный
учёт в БД, дерево делегирования в `hermes insights`, **пер-ходовой учёт**
(таблица `turn_usage`: промпт → токены/длительность/ошибки). Никаких денег
— только токены; данные — для анализа, не для UX.

## Инженерная база

Конвейер разработки: репозиторий → wheel → uv-tool установка (снимок,
не editable) → рестарт шлюзов; runtime закреплён pin'ами. Тестовая
дисциплина — ~36k тестов, герметичный раннер; живая приёмка на проде
обязательна («тесты показывают не всё»). Разработку ведёт агент
ZCode, а прод-агент — Локи, так зовут основного агента автора,
работающего в Telegram, — еженедельно верифицирует память живьём.

## Сквозные инварианты (несём во все подсистемы)

1. Кэш промпта неприкосновентен; контекст сессии не мутируется задним
   числом; любое дополнение — только новый текст в новом сообщении.
2. Нулевой след телеметрии в контексте модели.
3. LLM советует — детерминированный код решает (права, статусы, границы).
4. Исправление — новая ревизия, не стирание прошлого.
5. Расширять существующее, а не дублировать; новое ядро-поверхность —
   последнее средство.
